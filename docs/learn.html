Part 1The problem, and the decision to use LangGraph

The problem

When an alert fires, someone has to do the first line of incident response: read the logs, look at the metrics, find the right runbook, and decide whether this can be fixed now or needs a person. This project hands that first pass to cooperating agents and keeps a human in charge of the outcome.

  • An alert comes in with its logs, metrics, and runbooks.
  • Several agents with distinct roles investigate it, in parallel where the questions are independent.
  • The result is a brief where every conclusion cites the exact log line or metric behind it, with a resolve-or-escalate recommendation.
  • A console lets a person start the run and watch it happen.
  • Nothing is treated as final until that person approves it, and destructive steps need a typed confirmation.
  • Log text is untrusted: a line written to look like an instruction must not steer the agents.

Strip the words "agentic" and "orchestration" away and the program has to do this: read a folder of evidence, decide which specialist should look at what, run two specialists at the same time, merge what they found without losing either, look at the merged result and decide again, check the answer, stop dead until a person clicks, and then finish. That last list is the actual engineering problem.

Three items on it are hard to write by hand and easy to get silently wrong.

  1. The order is decided at run time. What runs after the planner depends on what the planner said. What runs after the checker depends on what the checker said. By hand that is a tangle of if-statements, and nobody reading the code can see that the routing is real.
  2. Two things run at once and write to the same place. By hand that is asyncio.gather and a merge we write ourselves. The merge is exactly where one careless line drops one agent's findings, and the bug looks like a model that missed something.
  3. The run must stop for a human and continue later. The pause happens inside an HTTP response. The click arrives minutes later on a different request. Something has to save the run and find it again.
So we decided on LangGraph. It is a Python library that does exactly those three things and nothing else: it runs your functions in an order described as a graph, merges parallel results by rules you declare once, and can pause and resume with saved state. It never sees a prompt and adds zero tokens. The pause is the one part we could have built another way; we use it so the human gate lives on the graph where it can be seen. The alternatives we weighed were plain Python with asyncio, and LangChain's agent classes, which hide the loop we most wanted to control.

Part 2LangGraph from the basics

Everything LangGraph does rests on three ideas. Read these three slowly; every later term is built from them.

1 · State: one dictionary everyone shares

You declare a Python dictionary with named keys. That dictionary is the whole memory of the run. Every function gets the entire dictionary as its argument. You write it as a TypedDict, which is a normal dict whose keys and value types are declared up front so readers and type checkers know what is in it.

from typing import TypedDict

class State(TypedDict, total=False):     # total=False: a key may be absent until someone writes it
    question: str
    answer: str
    tries: int

2 · Node: a function from state to a partial update

A node is a plain function. It receives the whole state. It returns a small dict containing only the keys it changed. It does not mutate the state and it does not return all of it. LangGraph merges the returned dict into the state.

def think(state):
    return {"answer": "42", "tries": state.get("tries", 0) + 1}

3 · Edge: what runs next

A fixed edge says "after A, always run B". A conditional edge names a router: a plain function that reads the state and returns the name of the next node. A router writes nothing; it only points.

from langgraph.graph import StateGraph, START, END

def route(state):
    return END if state.get("answer") else "think"

g = StateGraph(State)
g.add_node("think", think)
g.add_edge(START, "think")                              # fixed
g.add_conditional_edges("think", route, ["think", END]) # conditional; the list names every possible target
app = g.compile()
result = app.invoke({"question": "meaning of life?"})

START and END are the two terminals. compile() turns the description into something runnable. invoke() runs it to the end and returns the final state; stream() yields events as it goes.

4 · Supersteps: how the engine runs

The engine works in rounds called supersteps. In one superstep, every node that is due runs, possibly several in parallel. Then all their returned dicts are merged into the state. Then the routers on their outgoing edges run and decide what is due next. It stops at END or when it hits recursion_limit, a cap on the number of supersteps whose default is 25.

5 · Reducers: how two writes to one key are merged

If two nodes in the same superstep both return a value for the same key, LangGraph needs a rule. By default there is no rule and it raises InvalidUpdateError. You give the rule per key by wrapping the type:

import operator
from typing import Annotated

class State(TypedDict, total=False):
    claims: Annotated[list, operator.add]   # two lists arrive → concatenate
    tokens: Annotated[int, operator.add]    # two ints arrive → sum
    ledger: list                            # no reducer → plain overwrite. fine when one writer

6 · Send: run N copies of a node at once

A router may return, instead of a name, a list of Send(node_name, payload) objects. Each one launches a separate copy of that node in the same superstep. The payload is that copy's entire input. The copy does not see the shared state at all.

from langgraph.types import Send
def fan_out(state):
    return [Send("worker", {"job": j, "data": state["data"]}) for j in state["jobs"]]

7 · defer: wait for everyone

g.add_node("gather", gather, defer=True) means: do not run this node until nothing else in the graph is still pending. It is the fan-in that pairs with a fan-out.

8 · Checkpointer, interrupt, resume: pausing for a human

A checkpointer is a store where the state is saved after every superstep, keyed by a thread_id you pass in the run config. InMemorySaver keeps it in process memory. Inside a node, interrupt(payload) raises out of the run: the state is saved, the graph is marked as waiting at that node, and the payload is handed to the caller. Later, run the graph again with the same thread id and Command(resume=value) instead of an input. It re-enters the waiting node, and this time interrupt() returns value.

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

app = g.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "abc"}}

def approve(state):
    answer = interrupt({"question": "ok?"})     # first run: raises, run stops. resumed run: returns the answer
    return {"approved": answer}

app.stream({"x": 1}, cfg)                      # stops at approve
app.stream(Command(resume={"yes": True}), cfg) # continues from approve
The one trap. Resume does not continue a node from the middle. It runs the whole node again from its first line; only the interrupt() call behaves differently. Anything above it happens twice.

9 · Streaming: seeing inside while it runs

app.stream(input, cfg, stream_mode=["updates", "custom"]) yields events. updates means "a node finished, here is what it returned". custom means anything a node pushed by hand through get_stream_writer(). That is how a screen lights up mid-run.

That is all of LangGraph this project uses: state, node, edge, router, superstep, reducer, Send, defer, checkpointer, interrupt, Command, stream. Part 3 shows each one doing its job.

Part 3The solution: files, state, and the flow of data

The files

Everything that runs is under app/. Read the grey text as "the one thing this file is responsible for".

app/ ├── main.py HTTP. Serves the page, streams a run, takes an approval. ├── graph.py Wires the eleven nodes into a StateGraph. Compiles it with the checkpointer. ├── state.py The TypedDict every node shares, and which keys carry reducers. ├── nodes.py The eleven node functions and the two routers. ├── agent.py run_agent: the model-plus-tools loop every model-calling node uses. ├── llm.py converse: one calling shape over fixtures, Bedrock, Anthropic. ├── prompts.py Five system prompts and the two paragraphs all of them carry. ├── evidence.py Incident file → keyed records. The injection guard. Agent view vs audit view. ├── metrics.py Compare "12.4s" with "85ms" correctly. └── tools/ ├── specs.py The five tool schemas the model is shown. ├── grants.py Which role may call which tool. └── impl.py What the tools do. They are handed the redacted records only. web/index.html The console. One switch over the event stream. examples/ incident-input.json: the bundled incident in its input format. data/ incident.json (normalised from the example), runbooks.json (risk overlay). fixtures/ Recorded model replies, one file per role, for MOCK=1. tests/ 62 tests, all in mock mode.

Data goes down this stack as a request and comes back up as a partial state update. LangGraph sits in the middle layer only: it calls nodes.py and merges what comes back. It never sees anything below.

The state: one whiteboard, twenty-one keys

Before following the flow, know the whiteboard. This is app/state.py. Every key that will ever exist during a run is declared here, grouped by who writes it.

class IncidentState(TypedDict, total=False):
    # set once, then read-only
    incident: dict                         # the alert and the raw evidence, from the caller
    evidence: list[dict]                   # audit view: raw text. screen only
    agent_evidence: list[dict]             # agent view: redacted. the only thing models see
    quarantined: list[dict]                # what the guard removed, with the rules it tripped

    # written by parallel investigator copies: reducers required
    claims: Annotated[list[Claim], operator.add]
    trace: Annotated[list[dict], operator.add]
    tokens_in: Annotated[int, operator.add]        # and tokens_out, cache_read, cache_write

    # single writer each: no reducer, on purpose
    ledger: list[Claim]                    # collect writes it once per round
    open_questions: list[dict]             # triage proposes, collect clears
    round: int
    candidates: list[dict]                 # match_runbooks
    plan: list[PlanRow]                    # resolve
    decision: str                          # resolve
    verdict: dict                          # verify
    replans: int                           # verify
    brief: dict                            # render
    approved_ids: list[str]                # approve
    receipts: list[dict]                   # execute
LangGraph term · reducer, applied

The six keys under "parallel investigator copies" are the only ones two nodes can write in the same superstep, because investigate runs as several copies at once. Each carries operator.add. ledger holds the same Claim type as claims but has no reducer, because only collect writes it, once, after the copies are done. Reading the type alone tells you which part of the graph is concurrent. That is deliberate: without these reducers the run dies on the first two-question round with InvalidUpdateError.

Two shapes recur. A Claim is one thing an investigator believes: {kind, text, cites, confidence, by}, where kind is cause, symptom, ruled_out, or context, and cites is a list of evidence keys like log:4. A PlanRow is one proposed action: {id, action, risk, rationale, cites, runbook}.

Stage 1The run starts app/main.py · app/graph.py

Data inPOST /run with the incident in the body (or the one on disk).
Data outA fresh thread_id, a config, and the first state: {"incident": inc}. An open HTTP response that will stream frames.
# app/graph.py, at import time
app_graph = build().compile(checkpointer=InMemorySaver())
def run_config(thread_id):
    return {"configurable": {"thread_id": thread_id}, "recursion_limit": 40}

# app/main.py, per request
thread_id = str(uuid.uuid4()); cfg = run_config(thread_id)
for mode, chunk in app_graph.stream({"incident": inc}, cfg, stream_mode=["custom", "updates"]):
    if mode == "custom":  yield sse(chunk)                                 # a node called emit()
    else:                 yield from (sse({"e": "node", "node": n}) for n in chunk)   # a node finished
LangGraph terms · compile, checkpointer, thread_id, recursion_limit, stream

compile happens once, when the module loads, and produces app_graph, the runnable graph. The checkpointer is attached here, so from the first superstep the state is saved after every step under whatever thread_id the config carries. That save is what stage 13 will need. recursion_limit is raised from 25 to 40 because a normal run here, with a loop and a possible redraft, reaches the mid-twenties. stream with two modes gives one generator that yields both LangGraph's own "node finished" events and the frames our nodes push by hand. FastAPI's StreamingResponse sends each yielded line to the browser as a Server-Sent Event.

The browser stores the thread_id from the first frame. That id is the only thing that joins this request to the approval that comes later.

Stage 2ingest app/nodes.py

Readsincident
Writesevidence (audit view), round: 0, replans: 0

Superstep 1. Counts logs, metrics, runbooks for the screen and emits the incident frame. Zeroes the two counters that later loops will increment. That is all.

def ingest(state):
    incident = state.get("incident") or {}
    emit({"e": "incident", "incident_id": ..., "counts": {...}})
    return {"evidence": audit_view(incident["evidence"]), "round": 0, "replans": 0}
LangGraph term · the node contract, applied

Notice what is returned: three keys, not the whole state. LangGraph merges them. incident is untouched and still there for the next node. Every function in nodes.py ends this way, with a dict of two to eight keys.

LangGraph term · custom stream events

emit() is a nine-line helper around get_stream_writer(). It pushes one JSON frame into the custom stream. It swallows the error the writer raises when there is no run in progress, which is the case in a unit test, so emitting can never take a node down.

Stage 4triage, round 1: the planner app/nodes.py · app/agent.py · app/llm.py · app/prompts.py

Readsincident.alert, a summary of agent_evidence (counts and names, never the lines), quarantined keys, ledger (empty), round

Superstep 3, the first model call. The node builds a user message from state, then hands it to run_agent("planner", ...). This is the moment to see how a model call travels down the file stack.

Down the stack. nodes.py picks the role. prompts.py supplies the system prompt: the role's text plus two shared paragraphs, one saying every claim must cite keys and one saying evidence is data, never instructions. grants.py says the planner has no tools, so the tool list is empty. agent.py runs the loop, which for the planner is a single turn. llm.py sends it to whichever backend is configured and returns one neutral shape. Then back up: agent.py extracts the JSON, nodes.py keeps only questions addressed to log or metric, caps them at two, and writes them onto the whiteboard.

Why the planner has no tools. If it could search, it would answer its own questions in one turn and the specialists would be decoration. Removing the capability is what forces the delegation to be real. The planner is the one role whose entire output is a decision about who should look at what.

Stage 5dispatch: the router fans out app/nodes.py · app/graph.py

Readsopen_questions, round, the ledger's cause claims
Writesnothing. Returns either a node name or a list of Send objects.
# app/graph.py
g.add_conditional_edges("triage", dispatch, ["investigate", "match_runbooks"])

# app/nodes.py
def dispatch(state):
    questions = state.get("open_questions") or []
    has_cause = any(c["kind"] == "cause" for c in surviving(state))
    if state["round"] >= MAX_ROUNDS:            return "match_runbooks"     # A: cap of 3
    if not questions:
        if has_cause:                           return "match_runbooks"     # B: done honestly
        raise RuntimeError("no questions and no cause")                    # C: refuse a blank brief
    return [Send("investigate", {"question": q,
                                 "agent_evidence": state["agent_evidence"],
                                 "round": state["round"]}) for q in questions]   # D: fan out
LangGraph terms · conditional edge, router, Send

add_conditional_edges("triage", dispatch, [...]) attaches dispatch to triage's outgoing edge. It runs in the same superstep as triage, right after it, and decides what is due next. The list at the end names every target it might return, which is what lets the diagram be drawn from the code.

Branches A and B return a name, and one node runs next. Branch D returns a list of Send objects. Each Send("investigate", payload) launches a separate copy of the investigate node in the next superstep, and that copy receives only the payload as its input, not the whiteboard. That is why the payload packs agent_evidence explicitly: a copy sent only its question would have no evidence, every tool call would return nothing, and the symptom would point at the tools.

Round 1 in the recorded run: two questions, no cause yet. Branch D. Two copies.

Why the close condition is code. A model that may decide it is finished eventually decides too early or never. Branch B requires a claim tagged cause in the ledger. Branch A caps the rounds at three. Branch C refuses to produce a brief with nothing in it. None of those are requests in a prompt.

The tool loop, in agent.py. The model cannot read metrics. It produces a tool_use block asking for read_metrics. run_agent appends that assistant message to the transcript exactly as returned, calls run_tool in impl.py, and appends one user message holding every tool_result. Then it calls the model again. Three rounds, then a forced "answer now" with no tools offered. Two rules are hard API contracts: the assistant's request goes into the transcript before the result, and all results from one turn go back in one message.

The tools, in tools/. grants.py says the metric role may call read_metrics and compare_metric; specs.py supplies those two schemas and no others, so the model has no word for search_logs. impl.py is handed agent_evidence, the redacted list, and holds no reference to the raw one. compare_metric calls metrics.py, which parses "12.4s" and "85ms" into one unit family and returns 145.9 times worse; the naive float division would have reported an 85% improvement. The same parser matches unit suffixes longest first, so "63 sessions" is read as a count, not as 63 seconds.

Both copies finish inside superstep 4 and both return claims, trace, and token counts. LangGraph looks up each key in the state type. All six carry operator.add, so the two claim lists are concatenated, the two trace entries are appended, and the token counts are summed. Had any of them lacked a reducer, this is the moment the run would have died. Because claims only ever appends, it accumulates across every round of the run; the next stage handles that.

Stage 7collect: the fan-in and the citation check app/nodes.py · app/evidence.py

Readsclaims, ledger, agent_evidence

LangGraph term · defer, applied

g.add_node("collect", collect, defer=True). Both investigator copies have a fixed edge to collect. Without defer, collect would run as soon as the first copy finished, building the ledger from one branch out of two, and the bug would look like a model that missed something. With it, collect waits until nothing else is pending and runs once, in superstep 5.

The three checks. For each claim: keep only citation keys that resolve to a real record in index(agent_evidence); a claim left with none is dropped and the reason recorded. Skip a claim whose kind and text are already in the ledger, which is how the accumulating claims list is handled. Append the rest to the ledger. In the recorded run: 7 kept, 0 dropped, 7 in ledger. Then clear open_questions so the planner starts its next round clean.

resolvable = set(index(state["agent_evidence"]))
for c in state["claims"]:
    real = [k for k in c["cites"] if k in resolvable]
    if not real:                              dropped.append({**c, "why": "no citation resolves"}); continue
    if (c["kind"], c["text"]) in known:       continue
    kept.append({**c, "cites": real})
ledger.extend(kept)
return {"ledger": ledger, "open_questions": [], "trace": [{"node": "collect", "kept": 7, "dropped": 0}]}

From here every model reads surviving(state), the ledger entries with at least one citation, and never the raw claims. An ungrounded claim never reaches a second model.

LangGraph term · a fixed edge that points backwards

g.add_edge("collect", "triage"). A loop in LangGraph is nothing special: an edge whose target ran earlier. Superstep 6 runs triage again with the same prompt template and different state. This edge is what makes the design an orchestration rather than a one-shot fan-out: control returns to the planner and it decides again with new information.

ESTABLISHED SO FAR now lists the migration's CREATE INDEX on stock_levels holding the lock every write is queued behind, with CPU below baseline and a healthy replica ruling out compute and an outage. The planner returns zero questions and done: true. dispatch runs again: round 2 is under the cap, no questions, a cause exists. Branch B: match_runbooks. With a live model and a murkier incident, round 2 is where the planner would ask a follow-up built from both round-one answers, for example "writes are waiting but the database is idle, find what holds the lock". That question cannot be written into the program in advance, which is why the loop exists.

Dispatch simulator. Set the state after a triage, read the branch.

Stage 10resolve: the plan app/nodes.py · app/agent.py · app/tools/impl.py

Readssurviving(state), candidates, verdict if a previous one failed
Writesplan (rows sorted safest first), decision, trace, tokens

Superstep 8. The resolver's only tool is get_runbook, which returns the runbook body plus the overlay: per-step risk, not_when, human_follow_up. It read all three. The reply is normalised in code: risk must be read_only, reversible, confirm, or human or it becomes human; rows sort by risk; decision must be automate, escalate, or insufficient_evidence. In the recorded run: escalate, because RB-01 says "Rebuilding the index with CREATE INDEX CONCURRENTLY is a human decision", and its fastest mitigation, cancelling the migration backend, is gated behind a typed confirmation. RB-02, rolling back the deploy, is rejected with its own not_when quoted: rolling back application code does not release a running migration's lock. RB-03, restarting the pooler, is rejected because it is not for sessions blocked on a table lock. If a verifier had failed a previous plan, the objections are appended to this prompt with "address this"; that is the redraft path from stage 11.

def route_verdict(state):
    if verdict.get("pass"):                           return "render"    # 1
    if state.get("replans", 0) <= 1:                                    # first failure only
        if verdict.get("fails") == "evidence":        return "triage"    # 2: a gap. planner asks again
        if verdict.get("fails") == "plan":            return "resolve"   # 3: redraft once
    return "render"                                                      # 4: second failure. show the objection

Same mechanism as dispatch: a function on the outgoing edge that returns a name. Two of the three names are earlier nodes, so this is the second loop in the graph. def approve(state):
    gated = [row for row in state["plan"] if row["risk"] != "human"]      # cheap. it will run twice
    emit({"e": "await", "rows": gated})
    answer = interrupt({"question": "Approve which actions?", "rows": gated})
    valid = {r["id"] for r in gated}
    return {"approved_ids": [i for i in answer.get("approved_ids", []) if i in valid]}
LangGraph terms · interrupt and the checkpointer, applied

Superstep 11. interrupt() raises out of the run. Because the graph was compiled with InMemorySaver, the entire whiteboard, plan rows and all, is already saved under this thread_id, and the graph is marked as waiting at approve. The generator in /run finishes; get_state(cfg).next is non-empty, so the last frame says awaiting: true; the HTTP response closes. The browser unlocks the approval table using the rows from the await frame. Nothing has executed.

Look at what sits above the interrupt() line: one list comprehension and one emit. That is the replay trap handled. On resume this function runs again from its first line, and those two things happening twice cost nothing.

LangGraph terms · Command(resume), get_state

The same thread id finds the saved whiteboard. get_state(cfg).next lists the node the run is waiting at; empty means nothing to resume, hence the 409. Starting the graph with a Command instead of an input re-enters approve. Its interrupt() now returns the resume value, the node filters to ids that were actually offered, and writes approved_ids. The fixed edge carries the run to execute in superstep 12, which writes one receipt per approved row and lists the rest as skipped. Then END. The second stream closes with awaiting: false.

execute runs nothing. There is no tool in the process that could change the world, so the honest meaning of "execute" here is "record the human's decision with the runbook, the citations, and a note that no command was run". Three tests pin it: refusing a row leaves no receipt, approving nothing records nothing, an id the browser invents is ignored.
